Contextualização Arquitetural

Por que a Camada 3 é Vulnerável por Design?

1. Causa Raiz • RFC 791

Origem Sem Autenticação

  • O IPv4 transporta o campo Source IP, mas não valida criptograficamente o titular.
  • Roteamento padrão decide o caminho olhando apenas o Destination IP.
2. Ataque 1 • Identidade

IP Spoofing via ICMP

  • Construção de Echo Request (Type 8) via Scapy com origem declarada fictícia (RFC 5737).
  • Se o alvo responder (Type 0), o retorno vai para o IP declarado, não ao emissor real.
3. Ataque 2 • Disponibilidade

Mecanismo de ICMP Flood

  • Alto volume de solicitações em curto intervalo pressiona banda e processamento.
  • Demonstrado em laboratório por rajada controlada com rotação de origem.
Direcionamento no Laboratório: No reconhecimento inicial, SSH (:22) estava acessível e o MySQL restrito ao loopback (127.0.0.1:3306) → foco 100% direcionado às vulnerabilidades nativas da Camada 3.

Conceito Base • RFC 792

O que é o ICMP? (O Veículo do Spoofing e do Flood)

Funcionamento Normal (ping na Camada 3)

[Cabeçalho IPv4 (20 B) • Proto=1] → [Cabeçalho ICMP (8 B) • Type=8, Code=0, ID, Seq]
Característica 1 • Estrutura L3

Opera Direto na Camada 3

Não usa portas de Camada 4 (como :80 ou :443). Vai encapsulado direto no pacote IPv4 (Protocol = 1).

Característica 2 • Viabiliza o Spoofing

Sem Conexão (Sem Handshake)

Diferente do TCP (que exige 3-Way Handshake), o ICMP aceita qualquer pacote isolado que chega — ideal para IP Spoofing.

Característica 3 • Viabiliza o Flood

Processamento Obrigatório no Kernel

Cada Type 8 recebido obriga o kernel do alvo a interromper a CPU, alocar memória e tentar devolver um Type 0.

  • Burla bloqueio por IP fixo quando o atacante rotaciona o IP a cada pacote.
Ataque 2 • Sobrecarga Volumétrica (Disponibilidade)

O que é o ICMP Flood?

Disparo Massivo de Echo Request (Type 8)

Comparação entre o tráfego legítimo de diagnóstico e a rajada de Flood:

Ping Legítimo (1 por segundo) ~1,0 pps
Intervalo (Δt): ~1000 ms • CPU e fila de rede livres
Rajada de ICMP Flood ~50 a 400+ pps
Intervalo (Δt): 2 ms a 20 ms • Multiplicação abrupta de frequência!
*Em ataques irrestritos, ferramentas em baixo nível disparam milhares de pacotes/segundo visando esgotar o link e a CPU.
Impacto 1 • Rede

Saturação da Fila da Placa (Banda)

A enxurrada de pacotes ICMP Type 8 ocupa o buffer de recepção da placa de rede, atrasando pacotes legítimos.

Impacto 2 • Processador

Tempestade de Interrupções no Kernel

Cada pacote força a CPU a interromper tarefas (IRQ / softirq), validar checksum IPv4 e alocar estruturas de rede (sk_buff).

Impacto 3 • Resposta

Esforço Dobrado Tentando Responder

Sem filtragem, a Máquina Alvo gasta mais CPU e banda de saída montando um Echo Reply (Type 0) para cada pacote recebido.

Engenharia de Defesa na Camada 3

Como Mitigar ICMP Flood e IP Spoofing na Prática

1. DEFESA CONTRA ICMP FLOOD • CAMADA DE KERNEL

Rate Limiting por Limiar (nftables)

Filtra ICMP Type 8 Ignora IP de Origem Protege a CPU
Enxurrada Recebida
~50 a 400+ pps
IPs Rotativos (.10..59)
Filtro nftables
Limiar: máx. 5 pps
Burst: 10 pacotes
✓ ≤ 5 pps → ACCEPT
Ping legítimo responde
✕ > 5 pps → DROP
Excesso descartado na placa!
Comando no Alvo (Linux Kernel Firewall):
nft add rule inet filter input icmp type echo-request limit rate 5/second burst 10 packets accept nft add rule inet filter input icmp type echo-request drop
2. DEFESA CONTRA IP SPOOFING • ROTEADOR & HOST

Validação de Rota Inversa (BCP 38 / uRPF)

Checa Source IP Compara Tabela de Rotas Bloqueia Falsificação
Pacote Spoofado
SRC: 198.51.100.10
Entrou na LAN local
Checagem uRPF
Esperado: 192.168.1.0/24
Recebido: 198.51.100.10 (≠)
✓ IP da Sub-rede → ACEITA
Origem legítima (192.168.1.x)
✕ Rota Incompatível → DROP
Descarte imediato sem Type 0
Ativação no Kernel Linux (Strict Reverse Path) + Switch L2:
sysctl -w net.ipv4.conf.all.rp_filter=1 # Host/Roteador (RFC 3704 / BCP 38) Switch(config-if)# ip verify source # Switch LAN (IP Source Guard L2/L3)
